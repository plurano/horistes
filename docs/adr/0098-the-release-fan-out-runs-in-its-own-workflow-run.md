# ADR-0098: The release fan-out runs in its own workflow run

- **Status**: Accepted (amends [ADR-0031](0031-the-merge-train-app-runs-release-please.md), [ADR-0045](0045-the-merge-train-opens-no-release-pull-request-where-the-release-train-is-off.md) and [ADR-0096](0096-the-release-labels-module-leaves-the-release-step.md))
- **Date**: 2026-11-20
- **Authors**: Lusoris

## Context

The train's caller holds a workflow concurrency group until every job in its run ends. A release matrix in that run therefore holds the group while waiting for runners. In the measured fleet incident on 2026-11-20, the train job in run 44701216583 ended at 08:24:35Z; three release legs still waited at 08:33Z because their runner pods lacked CPU and memory. The scheduled 08:28Z train run 44702786399 waited behind that group. Earlier runs held it for 41–42 minutes. The regression reproduces this topology and the stalled train in [test_train_release_run.py](../../tests/test_train_release_run.py), using the bounded scheduler in [train_timeline.py](../../tests/train_timeline.py).

The scheduler reads rendered callers and reusable jobs, dependencies, runner expressions and concurrency groups. It models case-insensitive groups, one running and one pending entrant, replacement of the older pending entrant, running cancellation when requested, and workflow completion after all jobs end. Its six scheduled cycles use the template cron, eight-minute train jobs and unavailable release runners; its race scenarios use release runs ten minutes apart with fifteen-minute legs. These are explicit scenario bounds, not predictions of forge timing ([train_timeline.py](../../tests/train_timeline.py), [test_train_release_run.py](../../tests/test_train_release_run.py)).

## Decision

[merge-train.yml](../../.github/workflows/merge-train.yml) ends with the train job. Its sweep writes the same bounded release list to `GITHUB_OUTPUT` and, when `TRAIN_RELEASE_FILE` is set, a JSON file containing exactly `format: 1`, the original `TRAIN_HOLD_LABELS` string and `releases`. There is one list computation and one artifact writer; an unset path writes no file ([merge_train.py](../../tools/merge_train.py), `test_summary_release_file_matches_output` in [test_merge_train.py](../../tests/test_merge_train.py)). The sweep retains `release_off`. The train job drops its job outputs and grants `GITHUB_TOKEN` only `actions: write`, to dispatch the release caller from the same job that already holds the app key. This widens the token scope. The job uses the added scope only for workflow dispatch, and already holds the app key with its repository write rights; the checkout still persists no credentials. An upload step publishes `merge-train-releases` for one day, with missing files treated as errors, only when the run is not cancelled, the switch is on and the sweep produced a nonempty release list ([test_train_release_run.py](../../tests/test_train_release_run.py)).

After a successful upload, the train job runs `release_plan.py dispatch` with its run id and the `release_workflow` input, defaulting to `merge-train-release.yml`. The upload and dispatch share the cancellation, switch and sweep-output guards; dispatch also requires the upload outcome to be `success`. An empty release list uploads and dispatches nothing. There is no extra hand-off job waiting for a runner. The command reads the repository's default branch and sends one POST to the release workflow's dispatch endpoint with that branch as `ref` and both `train_run_id` and the upload step's `artifact-id` as inputs. It accepts HTTP 204 or 200 and never retries a dispatch, because a repeated POST starts another release run ([release_plan.py](../../tools/release_plan.py), [test_release_labels.py](../../tests/test_release_labels.py)).

The [release caller](../../templates/callers/merge-train-release.yml.tmpl) uses `workflow_dispatch` with a required string `train_run_id` and optional string `artifact_id` (default empty for a request by hand). A person with write access can dispatch it by hand with a train run id; the plan applies the same run checks. It deliberately has no workflow concurrency group. It grants only `actions: read` to its reusable call, so the plan can read the train run and download its artifact even while that run is still in progress. The reusable [merge-train-release.yml](../../.github/workflows/merge-train-release.yml) declares optional `artifact_id` (default empty), required `train_run_id`, `runner` and `app_client_id` inputs and `app_private_key` secret, with numeric `release_max_parallel` defaulting to 3 and `train_workflow` defaulting to `merge-train.yml`. It accepts no switch or hold-label input; the artifact carries the train's hold labels. The five-minute plan job checks out its own commit's modules without persisted credentials, downloads the identified artifact from `inputs.train_run_id` (or the named pattern when a manual request omits `artifact_id`) into a fixed runner-temporary path and publishes `releases` and `hold_labels` outputs ([test_train_release_run.py](../../tests/test_train_release_run.py)). An identified artifact must exist. A manual request with no id keeps the absent-pattern no-op.

Both commands refuse invalid input before any request: run ids and supplied artifact ids contain ASCII digits with no leading zero; dispatch requires an artifact id, and workflow names match `[A-Za-z0-9][A-Za-z0-9_.-]*\.ya?ml`, one file name without a path. HTTP 404 on dispatch names `.github/workflows/<release_workflow>` on the default branch and the caller template to add. HTTP 422 preserves the forge's detail, such as a caller missing `workflow_dispatch` or its `train_run_id` input. Either fails the step and leaves the train run red; there is no fallback ([test_release_labels.py](../../tests/test_release_labels.py)).

The `plan` command in [release_plan.py](../../tools/release_plan.py) validates before any release leg can mint an app token. [test_release_labels.py](../../tests/test_release_labels.py) covers these rules:

- A completed run with a conclusion outside `success` and `failure` produces a notice naming it, empty releases and empty hold labels, with exit 0. Failed sweeps may still supply a release list.
- The plan reads `/repos/{repo}/actions/runs/{train_run_id}` and the repository default branch with the existing bounded GET transport. The run path must equal `.github/workflows/<train_workflow>`. Only `schedule` and `workflow_dispatch` events qualify. The run head branch must equal the default branch, and its repository must equal the caller repository ignoring case. Status must be `in_progress` or `completed`, since the dispatching train job may still be finishing. Each refusal emits an error and exits 1 before the release file is read.
- Parallelism must be a whole number from 1 through 3. Invalid values emit an error and exit 3. The validation has moved out of the train's settings.
- With an artifact id, an absent file emits an error naming the id and exits 1. Without an id, an absent file produces the notice “train run uploaded no release list (switch off, or the sweep ended before its summary)”, empty releases and hold labels, and exit 0.
- A present file must be a JSON object with exactly `format`, `hold_labels` and `releases`. The format is integer 1. Hold labels are a string of at most 4096 characters without a newline or carriage return.
- Releases are a list of at most 256 objects, each containing exactly `owner` and `name`. The shared `MAX_RELEASES` definition lives in [release_workflows.py](../../tools/release_workflows.py) and also bounds the sweep writer. Owners start with an ASCII letter or digit and contain at most 39 letters, digits or hyphens. Names contain 1–100 ASCII letters, digits, dots, underscores or hyphens and cannot be `.` or `..`. Duplicate owner/name pairs are refused ignoring case.
- Invalid shape, malformed JSON and read failures emit an error and exit 1. Reading is bounded to one MiB of characters. An empty valid list produces a notice that no repository is named and exits 0. Valid plans write compact JSON `releases` and the original single-line `hold_labels` to `GITHUB_OUTPUT`.

The hand-off functions moved one-for-one from `release_labels.py` to [release_plan.py](../../tools/release_plan.py); test ids in [test_release_labels.py](../../tests/test_release_labels.py) remain unchanged.

The release job needs the plan and runs only when not cancelled and its release output is neither empty nor `[]`. It retains the `merge-train` environment, empty permissions, fifteen-minute timeout, fail-fast disabled, bounded matrix parallelism and the existing release steps. The settings step receives the plan's hold labels. Every leg's concurrency group includes the app client id and repository owner/name, independent of run id ([merge-train-release.yml](../../.github/workflows/merge-train-release.yml), [test_merge_train.py](../../tests/test_merge_train.py)).

## Alternatives

- A release caller triggered by `workflow_run` on train completion: rejected after the 2026-11-20 host check. Zizmor 1.31.1 with the pedantic persona, offline, returned 14 for `dangerous-triggers` with and without a branches filter. The unchanged rendered-caller contract runs zizmor without a config, and `tools/exceptions.py` refuses inline zizmor directives, so neither a config nor a directive can satisfy that contract ([test_render.py](../../tests/test_render.py)).
- A separate hand-off job in the train run: rejected because it waits for the same scarce runners while the train caller's `merge-train` workflow group remains held. This recreates the incident's stall ([train_timeline.py](../../tests/train_timeline.py)).
- A scheduled release caller polling the newest train run: rejected because it can schedule duplicate release legs on scarce runners and delay release work by up to one polling cycle. Dispatch identifies the exact run without polling.

The dispatch design uses the two forge facts checked against official documentation on 2026-11-20: GitHub Docs, “Triggering a workflow from a workflow”, states that `workflow_dispatch` and `repository_dispatch` create runs even when sent with `GITHUB_TOKEN`; the actions/toolkit artifact README (`packages/artifact/README.md`), “v2 - What's New”, item 2, states that artifacts uploaded with upload-artifact v4 or later are immediately available through the REST API before the run completes. These permit upload and dispatch in the train job.

## Consequences and migration

Queued release runners no longer hold the train caller's workflow group. Different repositories may release concurrently; the same repository has one leg at a time across runs. A newer pending leg replaces the older pending leg, which ends cancelled. The running leg is never cancelled by this policy. Release-please reads the default branch afresh, so the newer pending leg covers the replaced one. Case-insensitive group and pending-replacement scenarios, the old-layout stall and five planted concurrency defects are replayed in [test_train_release_run.py](../../tests/test_train_release_run.py).

Consumers must add the [release caller](../../templates/callers/merge-train-release.yml.tmpl) on their default branch and drop `release_runner` and `release_max_parallel` from the train call. Configure the release caller's `runner` and optional `release_max_parallel` there instead. The train and release callers may use different runner sets ([test_runner_labels.py](../../tests/test_runner_labels.py)). The train caller must grant `actions: write`, and the release caller must declare `workflow_dispatch` with a required string `train_run_id` and pass that input to the reusable call. Other caller file names are selected through the train's `release_workflow` and the release plan's `train_workflow` inputs. A missing release caller fails dispatch with the caller path and template to add; a caller missing the trigger or input fails with the forge's 422 detail. The two input removals, the removed release job and the new `actions` write scope are interface breaks, declared at version 0.3 in [interface.lock.json](../../interface.lock.json); [test_interface.py](../../tests/test_interface.py) verifies the version rule.

Artifact retention is one day. An automatic dispatch carries the upload's artifact id, so a missing or expired artifact fails the download; a successful download without the expected file also fails plan validation. A manual request with only `train_run_id` retains the absent-list notice and exit 0, and a valid empty list remains a no-op. The host checked the pinned [download-artifact source](https://github.com/actions/download-artifact/blob/9000827ccba6bdab643e8b6fd33ac0654aef8333/src/download-artifact.ts) on 2026-11-20: lines 104–137 reject an id lookup with no found artifacts, while lines 149–160 and 243–245 allow a pattern matching zero artifacts. The pinned [upload-artifact metadata](https://github.com/actions/upload-artifact/blob/cf430e030ddbb5b0abf93d22962f4752f3646cd9/action.yml) declares `artifact-id`. This lane replayed workflow wiring and local validation; it did not verify a live forge expiry or download. The separate run has its own status and cancellation lifecycle. Train switch-off prevents upload rather than cancelling already-started release runs ([merge-train.yml](../../.github/workflows/merge-train.yml), [test_train_release_run.py](../../tests/test_train_release_run.py)).
